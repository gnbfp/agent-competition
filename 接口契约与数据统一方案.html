五人协作：接口契约与数据统一方案

项目：运动生理闭环智能体（赛道三）　｜　适用：P1–P5 五人小组
一句话：先定契约，再写代码。 五个人不是靠"多沟通"统一，是靠三个存进仓库的东西统一——schema 文件、黄金样例、校验脚本。

一、核心思路：把"接口统一"变成一件可以自动检查的事

口头约定会漂移，文档会过期，只有能被程序验证的东西不会骗人。所以规则是：

  1. 每个人只产出一种 JSON（P2 出 activity、P3 出 metrics、P4 出 report、P5 只消费 report）；
  2. 每种 JSON 有对应的 schema 文件，字段名、类型、取值范围、枚举值全部写死；
  3. 仓库里放一份黄金样例（真实脱敏数据），五个人都拿它跑；
  4. 每次提交前跑 validate_contract.py，校验不通过就不能合并。

这样"统一"不靠人记，靠 CI 兜底：谁偷偷把 avg_hr 改成 average_heart_rate，脚本当场报错。

二、数据流：谁生产、谁消费、怎么验

数据产物生产者消费者契约文件校验
手表/CSV 原始记录用户导出P2——
activity.jsonP2 解析器P3、P4activity.schema.jsonschema + 跨字段规则
metrics.jsonP3 指标模块P4metrics.schema.jsonschema + 三法一致性

三条边界：

  • P2 不碰业务规则（只管把 CSV 变成干净数字）；
  • P3 不写报告文案（只管算出指标，不做判断）；
  • P5 不做任何计算（ACWR、TRIMP 一律不自己算，页面上每个数字都必须能在 report.json 里找到出处）。

最后一条是五人协作里最容易出事的地方：前端自己算一遍，后端也算一遍，两个数字对不上，答辩现场就露馅。

三、四条铁律（先背下来再开工）

铁律 1：单位统一，不许"看情况"

量单位示例错误写法
时长秒（_s）duration_s: 2880duration: "48分钟"
距离米（_m）distance_m: 8000distance_km: 8
配速秒/公里avg_pace_s_per_km: 360pace: "6'00""
心率bpm 整数avg_hr: 152avg_hr: 152.0 / "152"
负重/体重千克（_kg）weight_kg: 68.5weight: 68.5斤
温度摄氏度temp_c: 26temp: 26°
占比百分比 0–100long_run_max_pct: 300.3
比率小数（不是百分比）acwr_rolling: 1.62162%
日期YYYY-MM-DD2026-11-122026/11/12
时间戳ISO 8601 带时区2026-11-15T10:05:00+08:002026-11-15 10:05
文件编码UTF-8（无 BOM）—Excel 另存的 GBK / 带 BOM
配速是最容易出错的一个：手表导出常见 6'00"/km，一定要转成 360；前端展示时再转回去。转换函数只允许写一次，放在 P2 的 format.py 里。

铁律 2：缺失就是 null，不是 0、不是 ""、不是 -1

  • 心率没测到 → avg_hr: null，不能写 0（0 bpm 会污染所有平均值）
  • 没有 RPE → rpe: null（RPE=0 是"完全不费力"，是有效数据）
  • 没有海拔 → elevation_gain_m: null

配套要求：只要字段是 null，下游必须显式降级并写进 missing_data，而不是静默按 0 算。这正是答辩时"你怎么保证结果可信"的答案之一。

铁律 3：字段名 snake_case，枚举值写死

  • 字段名：avg_hr、resting_hr_delta、long_run_max_pct（不用 avgHR、Avg_HR）
  • 布尔字段用 is_ / has_ 前缀：consistency_ok、device_anomaly
  • 枚举必须来自固定表，不允许自由文本：
字段允许值
sportrun / bike / swim / strength / other
kind（计划日类型）rest / easy / tempo / interval / long / race / cross / other
level（风险等级）low / medium / high
acwr_statusundertrained / optimal / high / danger
rule_id正则 ^R\d{2}$（R01–R20）
tool（agent 工具名）load_activities / compute_load / estimate_vo2max / check_risk / retrieve_evidence / ask_athlete / generate_plan / explain

铁律 4：禁止"加字段不打招呼"

schema 里每个对象都写了 additionalProperties: false——多一个字段就校验失败。这不是刁难，是为了让"P2 临时加了个字段给 P5 用"这种暗箱操作当场暴露。

要加字段，走第六节的变更流程。

四、后端接口（HTTP 层）

报告页只有一个数据源：

错误统一格式（前端只需写一套处理）：

{"error": "not_found", "path": "/api/foo", "available": ["/api/health", "/api/report"]}

关键工程动作：contracts/mock_api.py 现在就能起，P5 不用等任何后端代码。

python contracts/mock_api.py --port 8080 --delay 300

它按真实接口的响应形状返回黄金样例，--delay 300 还能模拟 300ms 网络延迟，逼着前端把加载态写对。

五、五个保障机制（这才是"保证"的部分）

机制 1：schema 是唯一真源

contracts/*.schema.json 进仓库，改它 = 改所有人的约定，所以要 PR + 两人 review。代码可以重写，schema 不许悄悄变。

机制 2：黄金样例当"公分母"

samples/ 下四份 JSON 就是全队的共同语言：P2 要能产出与 activity_sample.json 同构的数据；P3 吃它出 metrics_sample.json；P4 吃它出 report_sample.json；P5 只吃最后一份。

判定标准很硬：同一份 samples，四个人各自跑，diff 必须为空（允许浮点容差 1e-6）。

机制 3：提交前自动校验

python contracts/validate_contract.py            # 校验 samples 四件套
python contracts/validate_contract.py --dir out/ # 校验自己产出的目录

校验器做两件事：

  1. schema 校验：类型、必填、枚举、正则、数值范围、未定义字段；
  2. 跨字段校验：JSON Schema 表达不了的业务一致性（见第七节）。

失败退出码 1，直接卡住合并。可以让 P4 配个 git pre-commit hook，一次配好全队受益。

机制 4：快照回归（防"改一处崩三处"）

把当前 report_sample.json 存成 baseline/report_v1.json。每次改完代码重跑，用 diff 看变化：

  • 变化是预期内（比如新增 hrv_rmssd 字段）→ 更新 baseline，并在 CHANGELOG 记一行；
  • 变化是意外（acwr_rolling 从 1.62 变成 16.2）→ 说明有人改了单位或算法，立刻查。

机制 5：契约变更必须"四处同步"

改 schema 时，四处一起改，缺一不可：schema 文件、samples、生产代码、消费代码。只改前两处 = 埋雷。

六、契约变更流程（照做，不要凭感觉）

步骤谁动作
1 提出任何人在群里写清：加/改/删哪个字段，为什么，谁受影响
2 定级P4只加可选字段 = 小版本（1.0 → 1.1）；改类型/改单位/删字段/改必填 = 大版本（1.0 → 2.0）
3 改契约P4改 *.schema.json + 同步 samples/ + 更新 CHANGELOG.md
4 自证提出人跑 validate_contract.py，全绿才提 PR
5 审查P2 或 P5 任一人重点看：消费方是否已同步、是否破坏历史数据
6 通知P4群里 @全体，附一行 diff 摘要 + 生效时间

大版本的特殊规矩：不删旧字段，只标 deprecated，保留一个阶段；且只在阶段交界处合并（避免并行开发期互相踩脚）。

七、跨字段校验规则（写在 validate_contract.py 里的业务一致性）

这些规则 JSON Schema 写不了，但恰恰是"数据真的统一"的证据：

编号规则抓什么错
C1activity_id 全局唯一重复导入同一条记录
C2max_hr ≥ avg_hr字段填反
C3配速与 duration_s / distance_m 推算值偏差 > 15s/km 报警配速与原始数据不同源
C4acwr_rolling 与 acwr_ewma 差 > 1.0 报警两个人用了不同口径（滚动 vs EWMA）
C5VO₂max 三法差异 > 5% 却标 consistency_ok: true一致性检查被写死成 true
C6plan.days 日期不重复、kind: rest 的 duration_min 必须为 0计划生成有 bug
C7每天必须至少挂一个 rule_id违反 R20 依据覆盖率（答辩必问）
C8report 里 plan 引用的 rule_id 必须在 risks/evidence 中找得到；反之依据不能空挂依据链断裂——本项目最致命的一类错

C8 尤其重要：如果报告里写了"ACWR 1.62 超标"却拿不出对应条款，这个项目在赛道三就失去了全部说服力。

八、开工第一天：90 分钟就位

时间谁做什么产出
0–30min全员把 contracts/ 拷进 Git 仓库，各自跑一遍 validate_contract.py，必须看到 4 个 PASS环境就绪

散会时的验收标准：P5 的页面已经在渲染 mock 数据，P2 的解析器已经在产出符合 schema 的 JSON，两边还没写过一行联调代码。

九、这个项目最容易踩的 8 个坑

  1. 配速格式：6'00"/km → 360 秒，转换只写一处，别每个模块各写一遍。
  2. CSV 带 BOM：Excel 另存的 CSV 开头有 \ufeff，Python 用 encoding="utf-8-sig" 读，否则第一个字段名变成 \ufeffdate，全部校验失败。
  3. 心率 0 当真值：手表没戴/没测到常导 0，直接进平均会把心率拉到 60，ACWR 全错。
  4. 跨零点跑步：按开始时间归属日期，写进约定，别一个模块按结束时间、一个按开始时间。
  5. TRIMP 男女系数不同（0.64/1.92 vs 0.86/1.67）：metrics.json 里必须能追溯用了哪个公式，否则两个人算出两个数值。
  6. 浮点直接比较：acwr == 1.62 永远为假，用 abs(a-b) < 1e-6。
  7. Excel 手工改数据：数字会变成文本（"152"），校验器能抓到类型错——这也是为什么必须跑校验器。
  8. 前端自己算指标：一算就和后端对不上。记住：页面上的每个数字都要能在 report.json 里找到出处。

十、验收清单（Definition of Done，10 条）

  • [ ] 1. python contracts/validate_contract.py 全绿（4 个 PASS）
  • [ ] 2. 四份 samples 都能被各自模块读取，无字段名适配代码
  • [ ] 3. report.json 里每个数字都能在前端页面上找到对应位置（无前端自算）
  • [ ] 4. 每个风险项都能顺着 rule_id → evidence.source 找到条款出处
  • [ ] 5. 所有 null 字段在下游有显式降级路径，并写进 missing_data
  • [ ] 6. 所有枚举值来自固定表，没有自由文本塞进枚举字段
  • [ ] 7. 单位全部符合第三节的表格（尤其配速、百分比、比率）

  • [ ] 10. 数据里不含真实姓名/位置轨迹/照片（脱敏后才进仓库）

十二、一句话收尾

五个人做同一个系统，统一靠的不是开会，而是把"什么算对"写进代码里。schema 说形状、样例说数值、校验器说对错——三样齐了，接口就不会在第五周爆炸。
