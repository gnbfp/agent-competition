# 运动生理闭环智能体 · 项目计划书 v0.1

> 赛道：AI＋跨学科融合创新（赛道三）｜五人小组｜初赛材料：本计划书 PDF + 3–5 分钟演示视频 + 可运行原型
> 状态：v0.1 草稿（2026-11-15），供内部对齐与初赛提交改写。**带 ⚠ 的地方是还没做完的，提交前必须补齐。**

## 一、一句话

**把手机上的一堆跑步数据，翻译成"这周该不该加量"的可解释决策——每一条结论都能指回一条规则和一份文献。**

## 二、问题：跑步的人不缺数据，缺判断

| 现状 | 具体表现 |
|---|---|
| App 给计划，不给理由 | 「本周跑量增加 10%」——为什么是 10%？什么情况下不该加？没人说 |
| 指标各算各的 | 手表说"负荷偏高"，另一个 App 说"恢复良好"，用户不知道该信谁 |
| 不会因为身体状态改决策 | 膝盖疼了照样推强度课，因为计划是上周排好的 |
| 数据不敢给 AI | 心率、睡眠、伤病主诉都是敏感数据，随便贴进对话框就是泄露 |

**用户的真实一句话**（本项目起点，来自队长本人）：*"半马前两周我的负荷已经到高危区了，但当时没人告诉我。"*

## 三、解决方案

### 3.1 输入

- 手表/App 导出的跑步记录（配速、心率、距离、时长、海拔）
- 一次比赛或体测成绩（用于反推有氧能力）
- 用户主观反馈：RPE（主观疲劳）、睡眠时长、疼痛主诉
- 环境：气温、湿度

### 3.2 处理（这是专业性所在）

| 步骤 | 专业内容 | 依据 |
|---|---|---|
| 算负荷 | TRIMP 心率加权训练冲量（男女系数不同） | Banister 1991 |
| 看变化 | ACWR 急慢性负荷比，**同时算滚动平均与 EWMA 两种口径并说明差异** | Gabbett 2016；Williams 2017 |
| 估能力 | VO₂max 三法交叉（Uth-Sørensen / Riegel / Daniels），差异 > 5% 判数据可疑 | Uth 2004；Riegel 1981；Daniels |
| 查风险 | 20 条规则（R01–R18 面向用户，R19–R20 是 agent 自校验） | 见 `contracts/rules.json` |
| 出计划 | 逐日安排（类型/时长/配速区间/心率区间），每条挂着 rule_id | 规则库 + 教练经验提纲 |
| 自校验 | agent 交计划前自己重算一遍负荷增幅与依据覆盖率，不通过就打回重排 | R19 / R20 |

### 3.3 输出（一份可回查的报告）

结论 → rule_id → 依据原文，例如：

> 本周 ACWR（EWMA 口径）1.62，超过 1.5 高危线 → **R06** → Gabbett 2016：负荷比 > 1.5 时伤病风险显著上升 → 建议下周总量降 30%、取消强度课 → 依据出处见 `rules.json#R06`

## 四、为什么这是「AI＋跨学科融合」，而不是套壳

| 评委可能问 | 我们的回答 |
|---|---|
| 换成别的领域也能做吗 | 换不了：TRIMP 的男女系数、ACWR 的窗口口径、心率漂移判有氧基础，这些是运动生理学的规则，不是通用 prompt |
| 专业知识到底改变了什么 | 改变了**判断**：同样 60 分钟，轻松跑与间歇跑的生理代价差 3–5 倍，里程相加看不出来；固定阈值判异常会把"加量期"误报成"过载" |
| 只交构想吗 | 已落地 4 份 JSON 契约 + 20 条规则库 + 校验器 + 假后端 + CSV 解析器（含 14 条单测） |

**智能体形态**：单 agent + 8 个工具（load_activities / compute_load / estimate_vo2max / check_risk / retrieve_evidence / ask_athlete / generate_plan / explain），主循环 Plan → Act → Observe → Self-check。三处必须让评委看见的自主行为：缺数据追问、条款检索换路、计划生成后自查打回。

> 明确不做多 Agent 编排：五人小队，多 agent 调试成本远大于收益，评委看的是"能不能自己决定下一步"。

## 五、技术方案（v1 零第三方依赖）

| 层 | 技术选择 | 理由 |
|---|---|---|
| 数据 | CSV 中间格式 → `activity.json` | 各家导出千奇百怪，统一在本队定义的 13 列 |
| 指标 | Python 3.12 标准库（statistics/math/json） | 评审机器可能只有干净 Python，不装包最稳 |
| 契约 | 4 份 JSON Schema + 黄金样例 + `validate_contract.py`（含 C1–C8 跨字段校验） | 五个人靠三样进仓库的东西统一 |
| Agent | 自研轻量编排（工具契约 + 状态 + 自校验循环） | 不引框架，答辩讲得清每一行 |
| 前端 | 原生 HTML/JS + SVG，只读 `report.json` | 页面不许自己算指标，保证前后端数字一致 |
| 隐私 | 数据脱敏 + `data/raw/` 不进 Git + 结果只留匿名 ID | 任何一次 push 等于公开发布 |

## 六、验证方案（每条都要出数字）

| 层 | 做法 | 通过标准 |
|---|---|---|
| L1 回测 | 队长 12 个月真实数据逐周回放 | 至少命中 1 次真实"掉速/不适"事件，预警提前 ≥ 3 天 |
| L2 一致性 | VO₂max 三法交叉 | 三法最大差异 < 5% |
| L3 对抗测试 | 注入 20 组脏数据（心率漂移、GPS 跳点、重复记录、单位错误） | 检出率 ≥ 90%，误报 ≤ 10% |
| L4 对照 | 5 名跑友 4 周对照（系统建议 vs 自己练） | 实验组 ACWR 落在安全区比例更高 |
| L5 专家评审 | 体育老师/校队教练盲评 10 份计划 | 合理性均分 ≥ 4.0（5 分制） |

⚠ 现状：L1 依赖队长导出真实数据（进行中）；L2/L3 可用样例 + 模拟数据先跑通；L4/L5 需找人，尚未开始。

## 七、创新点

1. **双口径 ACWR**：同时给滚动平均与 EWMA，并解释为什么两者不同——市面 App 只给一个数。
2. **依据覆盖率自校验（R20）**：计划里每条安排必须挂着规则与出处，空挂即打回——这是"可解释"的工程化落地。
3. **设备异常不入库（R02）**：心率 210/配速 7′00″ 这种数据判异常而不算出假负荷。
4. **疼痛优先（R15）**：与任何加量建议冲突时一律以安全为先，且不自动恢复原强度。

## 八、落地场景

- 校园跑团 / 体测备考（大学生体测、半马备赛是刚需）
- 校田径队与体育课的"训练计划合理性"辅助核查
- 后续可扩展到骑行、游泳（规则库按运动项扩展，不改架构）

## 十、风险与合规

| 风险 | 应对 |
|---|---|
| 医疗合规 | 全界面与文档写明「辅助参考，不替代医生诊断」；R15 触发时输出就医建议 |
